# amber — Threat Model

**Version:** 1.1
**Date:** 2026-06-16
**Author:** spacedudem
**Status:** Living document — update when architecture changes
**Methodology:** STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) + Privacy Threat Analysis

---

## Scope

This threat model covers the amber system in its v1 single-user deployment configuration:

- **Chrome Extension (Manifest V3):** content.js, background.js, popup.html/popup.js — running inside a user's Chrome browser on their workstation.
- **Go API Server:** running on the natsec host behind nginx, reachable at `https://korh.one` or a subdomain. Accepts POSTs from the extension, writes archives to disk, stores snippets in SQLite.
- **SQLite Tracker Database:** local to the server, contains stripped tracking code snippets and their Gemini Nano classifications.
- **Public GitHub Repository (spacedudem/amber-tracker-db):** server-pushed JSON export of the tracker database, regenerated by GitHub Actions on each push.
- **Data in transit:** HTTPS between extension and server, HTTPS between server and GitHub API.
- **Gemini Nano local inference:** the on-device AI classification step that runs inside Chrome's sandboxed process.

**Out of scope for v1:**
- Multi-user deployments where the server operator is not the extension user
- Physical access to the server or the user's workstation
- A compromised Chrome installation modified at the OS or kernel level
- Nation-state adversaries with certificate authority compromise capability
- The kage dependency (separate project with its own threat model)

---

## Assets

The following assets are worth protecting, ordered by sensitivity:

1. **User's active browser session (cookies, auth tokens, session storage):** During a capture, background.js fetches assets using the browser's existing cookie jar. Credentials for any site the user is authenticated to are implicitly available. This is the highest-sensitivity asset — exposure enables account takeover on any site whose session cookie is accessible during the fetch phase.

2. **Archived HTML content:** Saved archives may contain highly sensitive material — banking transaction histories, private messages, healthcare records, attorney-client communications, or corporate internal pages. Once written to disk the server operator can read any archive.

3. **Stripped code snippets before anonymization:** Between capture and the anonymization pass that removes URLs and domain names before public export, raw snippets may contain referring URL paths, embedded usernames, or session token fragments that could correlate a specific user to a specific page visit.

4. **Server API key:** Authenticates the extension to the server API. Exposure allows arbitrary archive submission and snippet injection into the public tracker database, both of which undermine the integrity of amber's public data product.

5. **Server disk (archive storage):** Archives stored at rest on the natsec host. A breach of the server's filesystem exposes all archived content.

6. **Public tactic database integrity:** The amber-tracker-db GitHub repository is consumed by the privacy community to build blocklists, filter lists, and research datasets. Poisoned or fabricated entries degrade the quality of every downstream tool that depends on amber's data.

7. **Gemini Nano classification results:** Local inference results that become the authoritative `tactic_type` label before storage. Manipulating the classification pipeline before the result is committed to SQLite would corrupt the tactic DB without leaving a detectable server-side footprint.

**Trust zone definitions:**

| Zone | Trust Level | Rationale |

| Web page JavaScript | Untrusted | Adversary-controlled; may attempt to manipulate extension behavior or exfiltrate data |

| background.js service worker | Medium | Extension-controlled; receives data from content.js, holds API key, performs network fetches |
| Gemini Nano (local inference) | High | Runs in Chrome's sandboxed ML process; output is classification text only |

| GitHub Actions runners | Low | Ephemeral, GitHub-managed compute; receives only already-anonymized export data |

## STRIDE Threat Analysis

### Spoofing

**T001 — Malicious website spoofs amber server endpoint to steal API key**

A page executing in the user's active browser session could attempt to exfiltrate the API key by (a) reading it from `chrome.storage.local` via a cross-extension messaging bug, or (b) registering a service worker at the same origin as the server to intercept the HTTPS POST. This is the primary credential-theft vector for an attacker who can place JavaScript on a page the user visits.

*Likelihood:* Low. MV3 isolated worlds prevent web page JS from calling `chrome.storage` directly. A cross-extension messaging attack would require either a vulnerability in Chrome's extension isolation or an amber extension that incorrectly exposes an external message listener.

*Mitigations:*
- API key is stored exclusively in `chrome.storage.local`, inaccessible to web page JavaScript in MV3 isolated worlds. The extension manifest does not declare an `externally_connectable` entry, so no web origin can send messages to the extension.
- HTTPS for all server communication prevents network-layer interception by a local MITM.
- The extension manifest and all source files published to the repository contain no hardcoded key. Reviewers and automated CI can grep for the pattern.
- Optional: `chrome.webRequest` certificate pinning for the korh.one TLS endpoint can be added to reject responses from certificates issued by unexpected CAs.

---

**T002 — Attacker spoofs an extension update to inject a malicious version**

An attacker who compromises the developer's Chrome Web Store account or the build pipeline could push a signed extension update that exfiltrates browsing session data, cookies, or the API key from every device where amber is installed.

*Likelihood:* Low for CWS-distributed versions (requires account compromise); elevated for self-installed unpacked extensions where the user controls the update source.

*Mitigations:*
- Chrome Web Store enforces extension signing and developer identity verification. Extensions cannot be silently updated by a third party.
- CWS developer account must use a dedicated Google identity with hardware-key two-factor authentication (FIDO2/Passkey). This is a process control, not a code control.
- For unpacked installs: the extension directory must be version-controlled in a private repository; updates applied only from a verified local path after manual diff review.
- The manifest pins no external CDN scripts — all extension JS is self-contained. This eliminates supply-chain injection via CDN.
- SHA-256 hash of the production `.crx` or unpacked directory is published in the project's `SECURITY.md` for each release, allowing independent verification.

---

**T003 — DNS or BGP hijack redirects the extension's POST to an attacker-controlled server**

A network-level attacker (ISP, hostile router, or rogue DNS resolver) redirects the extension's HTTPS POST to a server they control, capturing the archive payload and the API key sent in the request header.

*Likelihood:* Very low in general; elevated when the user is on a hostile network (public Wi-Fi, corporate network with SSL inspection).

*Mitigations:*
- HTTPS with a valid certificate is the primary control. A certificate mismatch causes the browser to abort the connection before transmitting the API key or archive payload.
- HSTS (`Strict-Transport-Security: max-age=31536000; includeSubDomains`) configured on korh.one prevents fallback to HTTP after first successful HTTPS contact.
- DNS-over-HTTPS configured in Chrome reduces DNS spoofing surface.
- The extension validates that the server URL scheme is `https://` before initiating any POST; a configured `http://` endpoint is rejected at startup with a warning in the popup.

### Tampering

**T004 — Man-in-the-middle modifies snippet data before it reaches the public GitHub repository**

An attacker positioned between the Go server and GitHub's API endpoint could modify the JSON payload in transit, injecting false tactic classifications or poisoning the tracker database with fabricated entries before they are committed.

*Likelihood:* Very low. Requires active MITM against a TLS session to `api.github.com` with a trusted certificate — a significant capability.

*Mitigations:*
- HTTPS between server and GitHub API; Go's `net/http` client validates the GitHub certificate chain by default using the system trust store.
- GPG-signed commits (v2 control): the server signs each push with an Ed25519 key. Anyone can verify the commit signature in the GitHub UI. An attacker who intercepts and modifies the payload would produce an unsigned or invalid-signature commit detectable by downstream consumers.
- The public repo's commit history is immutable once pushed; GitHub's own integrity controls prevent silent retroactive modification.

---

**T005 — Content script behavior tampered by malicious page DOM manipulation**

A malicious page can inject elements into the live DOM with fake `data-tracker` attributes, insert deceptive code patterns that inflate the amber tactic database with garbage, or remove genuine tracking elements to suppress accurate capture. Since content.js serializes the rendered DOM, this is a fundamental exposure.

*Likelihood:* Medium. Any page can manipulate its own DOM; this requires no special capability.

*Mitigations:*
- MV3 isolated world prevents the page's JavaScript from overwriting content.js functions, intercepting the postMessage channel between content.js and background.js, or reading the serialized output after it leaves content.js scope.
- This is a documented and accepted fundamental limitation of post-render DOM serialization. amber's security notes explicitly state: "captures reflect what the page chose to render at the moment of capture, which an adversarial page can influence." This is not a defect.
- Server-side snippet validation rejects snippets that fail structural integrity checks: empty snippets, suspiciously uniform text (repeated character runs), snippets lacking any JavaScript-like tokens, and snippets exceeding 16 KB.
- The k=3 export floor (see PT003) means a single adversarial page cannot cause garbage data to appear in the public DB unless it is corroborated by apparent captures from two other domains.

---

**T006 — Saved archive HTML tampered on disk after capture**

An attacker with write access to the server's archive directory (via a separate filesystem vulnerability, a compromised OS user account, or a future read/write API bug) modifies a saved HTML archive. The user is then deceived into reopening the tampered file, which has been updated to contain malicious content.

*Likelihood:* Low in v1 single-user deployment; higher if the server is ever multi-tenant.

*Mitigations:*
- At save time, the Go server computes a SHA-256 hash of the archive HTML and writes it to a sidecar `amber-meta.json`. On any subsequent access via the read API, the server re-hashes the file and returns an HTTP 409 with a tamper warning if the hashes differ. (v2 implementation; flagged as a gap in v1.)
- The archive directory is owned by the `amber` service account with `0750` permissions. Other OS users and the web server user cannot write to it.
- Archives are served with `Content-Security-Policy: default-src 'none'; style-src 'self' 'unsafe-inline'; img-src 'self' data:` — even if a tampered file contains a `<script>` tag, the browser blocks its execution.
- Archive files are not served publicly via nginx directory listing; access requires an authenticated API call.

### Repudiation

**T007 — Dispute over what tracking code was present on a captured page**

A website operator challenges the accuracy of a snippet attributed to their domain in the public tracker database, claiming the code was never present on their site, or was inserted or modified by amber. Without a chain of custody, amber cannot prove its data is accurate.

*Likelihood:* Low but plausible as amber's public dataset grows and becomes influential in privacy tooling.

*Mitigations:*
- The `amber-meta.json` sidecar (v2) records: original captured URL, precise UTC timestamp, SHA-256 of the full pre-strip HTML, and the amber version string used. This provides an immutable reference linking a specific snippet to a specific page version at a specific time.
- SQLite snippet records retain `captured_at`, `domain`, `url` (full, pre-anonymization), and `raw_snippet` in the server-side database. These server-side records constitute the authoritative chain of custody and are never exported verbatim.
- amber is open source; the stripping algorithm can be audited by any party to confirm it does not inject content, and the classification prompts are published.
- The server's `amber` binary is built with a reproducible build process; the binary hash is published alongside each release, allowing verification that the deployed binary matches the reviewed source.

---

**T008 — GitHub push attribution is unclear or deniable**

A push to the public amber-tracker-db repository from the server's GitHub PAT could be repudiated: it is unclear whether the data came from a legitimate amber deployment, a script, or a compromised token.

*Likelihood:* Low in single-operator scenario; relevant if the project grows.

*Mitigations:*
- Each JSON push to the public repo includes a `generated_by` object containing server version, Go build hash, and ISO-8601 generation timestamp at second precision.
- GPG-signed commits (v2) cryptographically bind each push to the server's signing key. The public key is published in the repository's `KEYS` file.
- GitHub's audit log records the authenticated identity (GitHub App or PAT owner) for every push; this log is available to the repository owner.

### Information Disclosure

**T009 — API key exposed in extension source or bundled package**

If the API key is present in any file within the extension package (manifest.json, any `.js` file, a config file), it is trivially extractable by anyone who downloads or installs amber, or by any automated scanner that indexes CRX packages.

*Likelihood:* High if hardcoded. Eliminated by current design.

*Mitigations:*
- The API key is never present in source code. It is stored in `chrome.storage.local` after the user enters it on the extension options page during first-run setup.
- The extension's GitHub repository contains no credentials. CI runs a secret-scanning step (`git grep` for patterns matching the API key format) as a pre-merge gate.
- If the `.crx` or unpacked extension directory is extracted and inspected, no key is present in any file. The key exists exclusively in Chrome's encrypted local storage on the user's machine.
- Key rotation: if the key is compromised, the user updates it in the options page; the server immediately invalidates the old key. Rotation does not require an extension update.

---

**T010 — User PII embedded in tracking snippets submitted to the public database**

Captured tracking code frequently contains user-specific values: email addresses passed to analytics functions, session tokens embedded in tracking pixel URLs, usernames in A/B test assignment calls, or device fingerprints tied to the user's specific browser. If such snippets are exported verbatim to the public GitHub repository, the user's PII becomes publicly accessible.

*Likelihood:* Medium-High. Tracking code embedding user values is the norm, not the exception.

*Mitigations:*
- Gemini Nano classification operates on code structure; the classification label (`tactic_type`) is what gets exported, not the raw user-specific parameters.
- The public GitHub export (`tracker_tactics.json`) contains only: domain hash, `tactic_type`, `severity`, and a sanitized representative snippet. Sanitization applies server-side before export: string literals matching email patterns, UUID v4 patterns, long alphanumeric tokens (>20 chars), and numeric sequences that resemble session IDs or timestamps are replaced with `[REDACTED]`.
- The full URL submitted with the snippet is dropped entirely before export; only the SHA-256 domain hash appears in public data.
- Raw snippets are retained only in the server-side SQLite database, accessible only to the server operator.
- Sanitization is a server-side pipeline step, not a client-side control, to prevent bypass by a modified extension.

---

**T011 — Sensitive archived page content exposed via server breach**

Archived pages may contain banking summaries, medical records, private correspondence, or confidential business documents. A successful attack on the natsec host's OS, the Go server process, or the nginx configuration would expose all archived content in plaintext.

*Likelihood:* Low (requires server compromise), but the potential impact is severe.

*Mitigations:*
- v1 acknowledges this risk explicitly: the user is both the server operator and the only person who decides what to archive. They bear full responsibility for the sensitivity of archived content.
- The archive directory is not served publicly by nginx. There is no unauthenticated URL that returns archive content.
- Disk encryption (dm-crypt/LUKS) on the natsec host protects against physical media theft. This is an infrastructure-level control outside amber's codebase.
- The Go server process runs as a dedicated non-root `amber` OS user with no login shell and no write permissions outside the archive directory and SQLite file.
- User documentation prominently warns: "Do not archive pages you would not be comfortable storing on a remote server you control."

---

**T012 — Server access logs expose user browsing patterns**

nginx and the Go server generate access logs that may include request URLs. Because the extension POSTs archives with the original source URL embedded in the request path or body, log files could reconstruct a detailed record of the user's browsing history for every page they archived.

*Likelihood:* Low (logs are on the private server), but a log file exfiltration would be a privacy breach.

*Mitigations:*
- The Go server logs only the domain name component of the source URL, not the full path or query string, for archive POST requests.
- nginx `access_log` uses a custom format (`$remote_addr $request_method $uri_path_only $status`) that excludes query strings and all request body content.
- Log files are retained for 7 days maximum, then deleted by logrotate. Logs are not shipped to any external SIEM or log aggregation service in v1.
- Snippet POST logs record only the `tactic_type` classification result, not the raw snippet text.

### Denial of Service

**T013 — Malicious page generates enormous or pathological DOM to overwhelm the extension**

A page could include millions of DOM nodes, deeply nested structures, circular references via Shadow DOM, or inject large amounts of content during serialization to exhaust memory in the content script, hang the browser tab, or crash the Chrome renderer process.

*Likelihood:* Low (requires user to navigate to and then capture a specifically adversarial page). Impact: tab crash or browser hang, not data exfiltration.

*Mitigations:*
- content.js enforces a hard limit: serialized HTML exceeding 10 MB triggers an immediate abort. The user sees an error in popup.html ("Page too large to archive — limit is 10 MB"). The capture is abandoned cleanly without writing partial data.
- DOM serialization runs inside a `Promise.race` with a 30-second timeout. Exceeding the timeout triggers the same abort path and popup error.
- Asset URL collection is capped at 500 distinct URLs per archive. Assets beyond this cap are recorded in `amber-meta.json` under a `truncated_assets` count rather than silently dropped.
- Background.js asset-fetch concurrency is limited to 6 parallel requests (matching Chrome's per-host connection limit) to prevent the extension from monopolizing browser network resources.

---

**T014 — Flood of large asset POSTs to server to exhaust disk or bandwidth**

An attacker who has obtained the API key sends a stream of maximum-size archive POSTs to `/api/archive`, attempting to exhaust disk space, saturate the server's bandwidth, or degrade server availability.

*Likelihood:* Low (requires API key). Impact: server DoS, potential disk exhaustion affecting other services on the natsec host.

*Mitigations:*
- nginx enforces `client_max_body_size 50m` for the `/api/archive` endpoint. Requests exceeding this are rejected with HTTP 413 before the Go server reads the body, preventing memory exhaustion.
- Go server wraps the request body with `http.MaxBytesReader` at the application level as a defense-in-depth measure against header smuggling attacks that bypass nginx limits.
- API key authentication is required on all write endpoints; unauthenticated requests return HTTP 401 without reading the body.
- nginx `limit_req_zone` rate limiting: maximum 10 archive submissions per minute per IP. This is a very conservative limit for a single-user tool and provides substantial headroom for legitimate use.
- The archive directory resides on a filesystem partition with a configured disk quota. If the quota is reached, the Go server returns HTTP 507 and alerts the operator via a cron-driven disk usage monitor (alert threshold: 80% of quota).

---

**T015 — Public tracker database spammed with garbage or adversarial snippets**

A party with the API key submits a high volume of fabricated snippets with false `tactic_type` labels to `/api/snippets`, corrupting the public database and by extension degrading the blocklists derived from it.

*Likelihood:* Low (requires API key). Impact: high — degrades public trust in amber's data.

*Mitigations:*
- Server-side structural validation before any snippet is inserted: must be non-empty; must be under 16 KB; must contain at least one JavaScript-like token (`function`, `var`, `let`, `const`, `=`, `(`, `)`, or `;`); must have a `tactic_type` value from the server-maintained enumeration of known tactic labels.
- The server does not accept a client-provided `tactic_type` as authoritative. The extension sends both the raw snippet and the Gemini Nano classification label. The server performs a second validation pass confirming the label is a known value; unknown labels are either re-classified server-side (v2) or stored as `unclassified` pending manual review.
- Snippet deduplication: SHA-256 of the raw snippet is computed server-side; duplicate snippets from the same domain within a 24-hour window are silently dropped, not inserted. This prevents trivial repetition attacks.
- The public GitHub export is a separate pipeline from insertion; the server can halt the export pipeline independently of snippet ingestion. In the event of suspected poisoning, the operator rolls back the public repo to the last known-good commit. GitHub preserves the full history.
- nginx rate limiting applies to `/api/snippets` at 60 requests per minute per IP.

### Elevation of Privilege

**T016 — XSS in archived HTML executes in the user's browser on reopen**

An archived HTML file contains a `<script>` tag, an HTML injection surviving amber's DOM-level strip pass, or an obfuscated payload (base64-encoded `data:` URI, split attribute injection, CSS `expression()` in legacy mode) that executes when the user reopens the archive in a browser tab. If the archive is served from the same origin as the amber server UI, the script could access the server's authentication cookies.

*Likelihood:* Medium. DOM-level stripping is more robust than regex but not perfect; sophisticated obfuscation techniques exist that exploit parser edge cases.

*Mitigations:*
- amber's stripping step operates on the live DOM after browser parsing and JavaScript execution, removing: all `<script>` elements (including those in Shadow DOM), all `on*` event attributes, all `javascript:` href/src values, all `<object>`, `<embed>`, and `<applet>` elements, and all `<iframe>` elements. DOM-level removal is immune to most parser-level injection bypasses.
- Archives are served with `Content-Security-Policy: default-src 'none'; style-src 'self' 'unsafe-inline'; img-src 'self' data:`. This header-level defense blocks script execution even if a `<script>` tag survives stripping — it is the last line of defense.
- nginx serves archives with `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`.
- Archives must be served from a separate subdomain or origin from the amber server's API/UI endpoints. This prevents a successful XSS in an archive from accessing amber API credentials via `document.cookie`.
- `data:` URI schemes in `src` attributes are restricted to `<img>` elements only during stripping. `data:` URIs in `<script src>`, `<link href>`, or `<iframe src>` positions are stripped.

---

**T017 — Path traversal in archive filename construction**

The Go server receives a domain name and URL path from the extension and constructs a filesystem path for the archive. A crafted domain value (e.g., `../../etc/cron.d/backdoor` or `../server.go`) could cause the server to write files outside the intended archive directory, enabling remote code execution if the attacker can write to a sensitive path.

*Likelihood:* Medium. Path traversal is one of the most common Go web server vulnerabilities when filenames derive from user input. The API key provides a false sense of security — an authenticated user with a compromised key can still attempt traversal.

*Mitigations:*
- The Go server extracts the hostname using `url.Parse().Hostname()`, then applies a strict allowlist regex `^[a-zA-Z0-9\.\-]{1,253}$` stripping any character not in that set before using the value as a directory name component.
- The full constructed path is resolved with `filepath.Abs()` before any filesystem operation; the resolved path is then verified with `strings.HasPrefix(resolvedAbsPath, archiveBaseDir+string(os.PathSeparator))`. If the resolved path escapes `archiveBaseDir`, the request is rejected with HTTP 400, the event is logged at ERROR level with the original domain and the constructed path, and no file operation is performed.
- `archiveBaseDir` is configured as an absolute path at server startup; a relative path value in the config causes the server to exit with an error at startup, preventing misconfiguration.
- The server process user (`amber`) has write permissions only to the archive base directory and the SQLite file location. OS-level permissions provide defense-in-depth: even if the path check were bypassed, writing outside the archive directory would fail with EACCES.

---

**T018 — SQL injection in snippet or archive storage**

The Go server inserts user-supplied data (domain, URL, raw snippet text, tactic type, Gemini Nano classification) into SQLite. If any SQL statement is assembled via string interpolation or `fmt.Sprintf`, an attacker with API access could inject arbitrary SQL commands, leading to complete database compromise, data exfiltration, or data deletion.

*Likelihood:* Low (Go's `database/sql` idioms strongly discourage interpolation), but the impact of a successful injection is complete SQLite compromise.

*Mitigations:*
- All SQL statements use parameterized queries exclusively via `database/sql` prepared statements. No `fmt.Sprintf`, string concatenation, or `+` operator appears adjacent to any SQL string in the codebase.
- A CI lint step (using `go vet` and a custom `sqlcheck` script) greps for `fmt.Sprintf` and string concatenation in any `.go` file within 5 lines of a SQL string literal. This fails the build if found.
- The SQLite file is not network-accessible. It is a local file accessible only to the `amber` process user. Even a successful SQL injection is bounded to the data within that database; it cannot reach the filesystem or execute OS commands in WAL mode with the server's restricted permissions.
- SQLite WAL mode is enabled; the database file permissions are `0600` owned by the `amber` user.

---

**T019 — Extension abuses `<all_urls>` host permission beyond declared purpose**

The extension declares `<all_urls>` in `host_permissions` to allow fetching assets from arbitrary domains using the user's session cookies. A compromised, trojaned, or modified version of amber could exploit this broad permission to silently fetch arbitrary URLs, exfiltrating content from any authenticated session without user awareness.

*Likelihood:* Low in honest deployment. High if the extension is trojaned (see T002). This is the highest-impact permission amber holds.

*Mitigations:*
- The asset fetch logic in background.js is restricted to URLs that appear in the asset URL list generated by content.js during a user-initiated capture. The fetch function is not callable with an arbitrary URL from any other code path.
- background.js does not register any external message listeners (no `externally_connectable`), so no web page or other extension can invoke the fetch capability.
- Content Security Policy in popup.html uses `default-src 'self'` preventing injection of additional scripts into the extension context that could redirect the fetch capability.
- The extension does not use dynamic `chrome.scripting.executeScript` calls at runtime; all content script injection is declared in the manifest.
- amber is open source; the fetch code path is fully auditable. Any fetch call outside the documented asset-retrieval flow is visibly anomalous in the source.
- `<all_urls>` is a justified permission with documented rationale. The Chrome Web Store listing explicitly explains the permission requirement.

## Privacy Threat Analysis

**PT001 — Extension reads all page content during capture**

During a capture, content.js has full read access to the rendered DOM, including authenticated content, form field values, and any text or markup visible on the page. Capture of a login page could include password field values if the browser has autofilled them and amber does not explicitly exclude them.

*Risk level:* Accepted — this is required functionality. The extension cannot strip tracking code without reading the page.

*Mitigations in place:*
- The extension is fully open source; the complete scope of data access is auditable by any party before installation.
- Capture is strictly user-initiated (one click on the popup button); no automatic capture, no background capture, no capture on page load.
- No page content is transmitted to any third party. Data flows only to the user-configured server endpoint over HTTPS.
- `chrome.storage.local` stores only the API key and user preferences; no page content is persisted beyond the current capture operation.
- Sensitive field types are explicitly excluded from DOM serialization: `input[type="password"]`, `input[type="credit-card"]`, and any element with `autocomplete="cc-number"` or similar attributes are replaced with an empty placeholder element in the serialized output.

---

**PT002 — Server operator can read all archived pages**

In a single-user deployment, server operator and extension user are the same person — this is not a risk. However, if amber is ever deployed in a shared or multi-tenant configuration, the server operator gains read access to all users' archived content, which may be highly sensitive.

*Risk level:* Accepted for v1 (single-user only). Must be re-evaluated before any shared deployment.

*v1 mitigations:*
- Documentation explicitly states that amber v1 is personal/single-user only and that archived content is stored unencrypted on the operator's server.
- The archive read API (`GET /api/v1/archives`) requires API key authentication in v1; in a multi-user scenario the same key would grant cross-user access — this is why multi-user is explicitly out of scope.

*Required before multi-user deployment (v2):*
- Per-user encryption of archive content using a key derived from user credentials (server never holds plaintext decryption key).
- Separate API key per user with server-side access control enforcement.
- Access control list on `GET /api/v1/archives` preventing cross-user archive reads.

---

**PT003 — Public snippet database enables re-identification of the amber operator**

A very specific code snippet — one that appears on only one internal corporate page, a private community, or a niche site — could reveal that the amber operator visited that specific page when the snippet appears in the public `amber-tracker-db` repository. Correlation of unusual snippets with known page fingerprints could de-anonymize the user's browsing.

*Risk level:* Low-Medium. Mitigated by design.

*Mitigations:*
- Domain is SHA-256 hashed before export. SHA-256 without salt is used because the goal is correlation grouping (grouping multiple snippets from the same domain), not hiding the domain from a determined party who could enumerate known domains. This is documented behavior, not a hidden weakness — the hash is for grouping, not secrecy.
- Full URL is stripped entirely from exported records. Only the domain hash appears. No page path, query string, or fragment is ever exported.
- No user identifiers are exported: no extension instance ID, no IP address, no timestamp more precise than day-level granularity.
- **k=3 anonymity floor:** snippets that appear in captures from fewer than 3 distinct domain hashes are not exported to the public database. This floor prevents the "unique page" re-identification scenario: if a snippet appears only on one private internal page, it will never reach the public DB because it cannot meet the k=3 threshold.
- The export pipeline is a separate code path from storage. The server-side SQLite database retains full context (URL, timestamp, raw snippet) for audit purposes, while the public export pipeline applies all privacy filters before any data leaves the server.

## Cryptography

| Use | Algorithm | Key Management |
|-----|-----------|----------------|
| Extension-to-server transport | TLS 1.2+ (enforced by nginx `ssl_protocols` directive) | Certificate via Let's Encrypt / certbot; auto-renewed 30 days before expiry |
| API key storage on client | AES-256-GCM (Chrome's internal `chrome.storage.local` encryption) | Chrome profile key; managed by OS keychain (Keychain on macOS, libsecret on Linux) |
| Domain hashing in public export | SHA-256, no salt (by design; see PT003) | No key required |
| Asset content addressing for deduplication | SHA-256 | No key required |
| Archive integrity verification (v2) | SHA-256 of full HTML at capture time | Stored in `amber-meta.json` sidecar alongside archive |
| Snippet deduplication | SHA-256 of raw snippet text | No key required |
| GitHub commit signing (v2) | GPG with Ed25519 curve | Server signing key in GPG keyring; passphrase stored in secret manager on natsec host |

**Design constraint: No custom cryptography.** All cryptographic operations use the browser's native WebCrypto API, Go's standard library `crypto/tls` and `crypto/sha256` packages, or platform-managed storage encryption. This constraint is enforced in code review — any PR introducing a custom crypto routine is automatically rejected.

TLS cipher suite configuration on nginx excludes: RC4, 3DES, export-grade ciphers, and MD5-based MACs. Only AEAD cipher suites (AES-GCM, CHACHA20-POLY1305) are permitted.

## Dependency Risks

**Chrome Prompt API (window.ai / Gemini Nano)**
- Controlled entirely by Google; behavior, availability, and API surface can change without amber's involvement.
- Model weights and inference logic are opaque — classification results cannot be independently verified against the model's reasoning.
- Context window limit (~4096 tokens) means large minified JS must be chunked before classification. Chunking at token boundaries may split a tracking tactic across two chunks, causing misclassification of both halves.
- *Mitigation:* amber treats Gemini Nano classification as best-effort. If `window.ai` is unavailable or returns an error, content.js falls back to submitting snippets with `tactic_type: "unclassified"` rather than blocking the capture. The server accepts unclassified submissions and flags them for future re-classification. Archiving never fails due to AI unavailability.
- *Mitigation:* Pin to the specific Origin Trial version documented in the README; monitor Google's deprecation channel for Prompt API announcements. Maintain a fallback classification path using a curated local regex ruleset for the most common tactic patterns (canvas fingerprinting, session replay injection, ad beaconing) that does not require Gemini Nano.

**mattn/go-sqlite3 (CGO dependency)**
- CGO dependency introduces native code (C) that adds memory safety risk absent from pure Go code. A buffer overflow or memory corruption vulnerability in SQLite's C layer could result in server compromise.
- SQLite itself has an outstanding security track record; the attack surface via go-sqlite3 is narrow because user input reaches SQLite only through parameterized queries.
- *Mitigation:* Pin go-sqlite3 to a specific version in `go.mod` with a `go.sum` lock. Audit go-sqlite3 and SQLite release notes for security advisories before upgrading.
- *Mitigation:* The Go server never executes user-provided SQL strings; all database interaction is through `database/sql` prepared statements, eliminating the most common SQLite attack vector.
- *Alternative path:* `modernc.org/sqlite` is a pure-Go SQLite port with no CGO dependency. If CGO becomes a deployment constraint or a SQLite vulnerability requires rapid mitigation, migration to `modernc.org/sqlite` is straightforward — the `database/sql` interface is compatible.

**GitHub API and GitHub Actions**
- GitHub rate limits: authenticated PAT allows 5,000 API requests per hour. A large batch export (thousands of snippets) must fit within this limit.
- *Mitigation:* The server batches all pending snippets into a single JSON document per export cycle and makes one push commit per batch, regardless of snippet count. Export frequency is configurable; default is once per hour.
- GitHub Actions runners are ephemeral, GitHub-managed compute with access to whatever the workflow receives as inputs.
- *Mitigation:* The export workflow receives only the already-anonymized tracker JSON (processed through all privacy filters server-side before push). No raw snippets, no archive content, no API keys, and no server credentials are ever transmitted to GitHub or used in GitHub Actions.
- GitHub service disruption would halt public DB updates but would not affect archiving — the server-side SQLite database continues accumulating snippets and archives independently. The export pipeline is non-blocking.

**Chrome Web Store (for public distribution)**
- CWS account compromise is the highest-impact supply chain risk (see T002).
- CWS review may reject extensions using Origin Trial APIs not yet available via token for public distribution.
- *Mitigation:* Dedicated Google account for CWS developer identity, separate from personal accounts, with FIDO2 hardware key two-factor authentication.
- *Mitigation:* Origin Trial token request submitted to Google's origin trial portal for the Chrome Prompt API; token embedded in manifest for distributed versions. Personal use installs work via the `#optimization-guide-on-device-model` Chrome flag without a token.

## Out of Scope

The following threat categories are acknowledged and explicitly excluded from this threat model's active mitigations. They are not ignored — they are consciously accepted as outside the risk boundary of a personal archiving tool at this deployment scale:

**Physical access to server:** An adversary with physical access to the natsec host can defeat all software controls. This is an infrastructure and physical security concern. Addressed at the hosting level (data center physical controls, LUKS disk encryption against media theft).

**Compromised Chrome installation:** If the user's Chrome browser is compromised at the OS or kernel level by malware running as the browser user or with root access, all extension security properties are void. amber cannot defend against a compromised browser host.

**Nation-state adversaries with CA compromise capability:** An adversary capable of issuing fraudulent TLS certificates trusted by Chrome for korh.one could conduct undetectable MITM attacks against the extension-to-server channel. HSTS and Certificate Transparency monitoring reduce this risk but cannot eliminate it. This is out of scope for a personal privacy tool.

**Gemini Nano model poisoning:** Google controls the model weights deployed as Gemini Nano in Chrome. A deliberately degraded, adversarially fine-tuned, or subtly backdoored model version could produce systematically incorrect tactic classifications. amber cannot detect or defend against this. Accepted as an inherent risk of dependency on a closed-weight in-browser AI.

**Side-channel attacks on local inference:** Timing, power, or cache analysis of Gemini Nano inference to reconstruct classified snippet content from external observation. This threat requires physical proximity or OS-level access and is out of scope for amber's threat model.

## Residual Risks

These are threats that have been analyzed, found to be real, and deliberately accepted — either because the mitigation cost exceeds the benefit at v1 scope, or because a full mitigation requires architectural changes planned for v2.

**RR001 — Archives stored unencrypted on server disk**
*Accepted for v1.* The server operator is the user. Encrypting archives at rest would require key management infrastructure (key derivation, key storage, decryption on access) that adds significant complexity for what is currently a single-user personal tool. If the server is breached, archived content is exposed. Risk is bounded by the user's judgment about what to archive and the quality of the server's access controls and OS security posture. Must be re-evaluated before any multi-user deployment.

**RR002 — DOM-level stripping may miss heavily obfuscated tracking code**
*Accepted as a fundamental technical limitation.* amber cannot guarantee 100% removal of tracking techniques. Sophisticated obfuscation methods — dynamically assembled script strings evaluated via `Function()` constructor, WebAssembly beacons, CSS-based exfiltration via `background-image` requests to tracker domains, or timing-based fingerprinting via `requestAnimationFrame` — may not be detected by DOM-level stripping. The archive will contain non-functional code fragments from stripped scripts, but undetected surviving obfuscated code cannot execute due to the `Content-Security-Policy: default-src 'none'` header applied to served archives. amber's user documentation states clearly: "amber removes known tracking patterns; novel or heavily obfuscated techniques may not be detected."

**RR003 — `<all_urls>` host permission is broader than minimally necessary**
*Accepted.* The alternative — requesting per-domain permissions before each capture — would require a UI confirmation dialog for every new domain, breaking the one-click UX that is central to amber's value proposition. The permission is justified by the core use case (fetching assets from any domain the user has navigated to), is disclosed in the extension's permission rationale statement, and is constrained programmatically to the asset URL list generated during capture. This is documented as a deliberate design trade-off.

**RR004 — Gemini Nano classification accuracy is not formally validated**
*Accepted for v1.* Gemini Nano at ~1.8B parameters with a 4096-token context window will produce false positives (classifying non-tracking code as a tactic) and false negatives (missing a tactic type). The k=3 export floor and the public GitHub repository (where the privacy community can challenge and correct misclassifications via Issues) partially compensate. A formal accuracy benchmark against a labeled ground-truth dataset of known tracking techniques is a v2 goal.

**RR005 — Single API key with no per-client revocation granularity**
*Accepted for v1 (single-user deployment).* In a single-user scenario, the API key is effectively a personal secret. If compromised, the user rotates it via the options page and the old key is invalidated server-side. In a hypothetical multi-user deployment, a leaked key for one user cannot be distinguished from legitimate requests and provides no way to revoke only that user's access without disrupting others. A per-client key system with server-side revocation is a prerequisite for any multi-user deployment.

**RR006 — Gemini Nano classification runs after DOM stripping, not before**
*Accepted architectural trade-off.* The classification step receives already-stripped snippet fragments, not the full original script. This means the classification context is limited to the extracted snippet rather than the surrounding code that might clarify its purpose. A false negative (e.g., a fingerprinting call misclassified as "analytics") is possible due to loss of context. The alternative — classifying before stripping — would require Gemini Nano to process large, minified complete scripts, consuming the entire context window on boilerplate before reaching the relevant code. The current approach optimizes for classification of the stripped code at the cost of contextual accuracy.
